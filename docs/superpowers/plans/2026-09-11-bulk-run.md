# Bulk Run Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the mobile client run a CSV import's queued searches — the verb
P3a deliberately withheld.

**Architecture:** A stateless `POST /searches/run-chunk` takes a
`csv_import_id`, runs the next slice of that import's not-yet-run searches
inside the same bounds the panel uses, and reports per-id outcomes. The client
holds no queue of ids: it calls repeatedly until `remaining` reaches zero. Run
state lives in the `car_searches` rows, so resume is the same request as the
first chunk.

**Tech Stack:** Laravel 13, Sanctum, PHPUnit; Expo 57, React Query 5,
react-native-reanimated 4.6 (already present), expo-keep-awake.

**Spec:** [`docs/superpowers/specs/2026-09-11-bulk-run-design.md`](../specs/2026-09-11-bulk-run-design.md)

## Global Constraints

- Laravel tests run in the container:
  `docker run --rm -v "$PWD":/app -w /app cars-ci-php:8.3 php artisan test`
- **`vendor/bin/pint --test` is a CI gate.**
- Mobile tests run on the host from `mobile/`. **Never add a dependency to the
  repository-root `package.json`** — use `npx expo install` inside `mobile/`.
- **There are no model factories.** Build rows with
  `ApiTestCase::search(User, $overrides)`, `::image(CarSearch, $overrides)` and
  `::csvImport(?User, $overrides)`.
- **No test may reach Wikimedia.** `Http::fake()` in every test that runs a
  search. `BulkRunProgressTest` is the reference for all three patterns:
  - `config()->set('cars-images.bulk_run_sleep_seconds_between_queries', 0)`
    so pacing does not make the suite crawl
  - `config()->set('cars-images.bulk_run_max_queries_per_chunk', N)` to force a
    bound without creating N+1 rows
  - `Http::fake(['*' => Http::response('Too Many Requests', 429)])` for the
    block path
- `@testing-library/react-native` 13.3.3: `render()` is synchronous. **Never
  `await render(...)`.**
- **`mobile/jest.config.js` must not be modified.** Per-file
  `/** @jest-environment jsdom */` docblock instead.
- Test `QueryClient`s: `gcTime: 0` for observed queries; `gcTime: Infinity`
  when seeding; `mutations: { gcTime: 0 }` **separately**.
- Screens using `Link`/`useRouter` cannot be mounted. Logic goes in hooks.
- **`npm run routes:types` after any route change**; **`npm run
  check:redirects` must pass.**
- **`ContractFixturesTest` must stay green on `login.json` without
  regeneration.**
- Never write `make_confirmed` or `year_confirmed` from the client.
- **No queue worker, no scheduling, no background execution.** A run that
  continues after its driver has gone is what this design refuses.

- [ ] **Step 4: Implement the action**

```php
<?php

namespace App\Services\Search;

use App\Exceptions\WikimediaBlockedException;
use App\Models\CarSearch;
use Throwable;

/**
 * One bounded slice of a CSV import's outstanding searches.
 *
 * The mobile equivalent of ListSearchQueries::runNextChunk(), with one
 * difference: that method drains a queue held in Livewire component state,
 * while this one re-selects from the database each call. The rows are the run
 * state, so a client that crashed mid-run resumes by calling again - no queue
 * to rebuild and nothing to hand back and forth.
 *
 * Bounded by a query count AND a wall clock, because there is no queue worker
 * on this host and a chunk has to finish inside max_execution_time. A slow
 * Commons cannot drag one call past the limit.
 */
class RunChunkAction
{
    public function __construct(private readonly RunSearchQueryAction $runSearch) {}

    public function execute(int $csvImportId): RunChunkResult
    {
        $maxQueries = (int) config('cars-images.bulk_run_max_queries_per_chunk');
        $maxSeconds = (int) config('cars-images.bulk_run_auto_chunk_seconds');
        $sleepSeconds = (int) config('cars-images.bulk_run_sleep_seconds_between_queries');

        // Ordered by id: CSV order, so a resumed run continues where the
        // import created its searches rather than wherever the engine
        // happens to return them.
        $queue = $this->runnable($csvImportId)->limit($maxQueries)->get();

        $startedAt = microtime(true);
        $outcomes = [];
        $blocked = null;

        foreach ($queue as $index => $search) {
            if ($index > 0 && microtime(true) - $startedAt >= $maxSeconds) {
                break;
            }

            try {
                $this->runSearch->execute($search);
                $outcomes[] = $this->describe($search, 'completed');
            } catch (WikimediaBlockedException $e) {
                // A block is not a per-query failure. RunSearchQueryAction has
                // already written the block event and the error event; all this
                // has to do is stop asking.
                $blocked = ['status' => $e->statusCode, 'retry_after_seconds' => $e->retryAfterSeconds];

                break;
            } catch (Throwable) {
                // One bad query is already marked `failed` and can be re-run.
                // Abandoning the chunk for it would strand everything behind it.
                $outcomes[] = $this->describe($search, 'failed');
            }

            if ($sleepSeconds > 0 && $index < $queue->count() - 1) {
                sleep($sleepSeconds);
            }
        }

        return new RunChunkResult(
            outcomes: $outcomes,
            ranSeconds: round(microtime(true) - $startedAt, 2),
            // Counted after the slice, not inferred from what was sent, so the
            // client's figure survives a dropped response.
            remaining: $this->runnable($csvImportId)->count(),
            blocked: $blocked,
        );
    }

    private function runnable(int $csvImportId)
    {
        return CarSearch::query()
            ->where('csv_import_id', $csvImportId)
            ->whereIn('status', ['pending', 'failed'])
            ->orderBy('id');
    }

    /**
     * @return array{id: int, make: string, model: ?string, from_year: int, outcome: string}
     */
    private function describe(CarSearch $search, string $outcome): array
    {
        return [
            'id' => $search->id,
            'make' => $search->make,
            'model' => $search->model,
            'from_year' => $search->from_year,
            'outcome' => $outcome,
        ];
    }
}
```

**Note on `skipped`:** the spec describes a `skipped` outcome for a row deleted
or finished mid-run. This implementation re-selects each call rather than
draining a held queue, so such a row simply is not selected — there is nothing
to skip. **Do not add a `skipped` branch that cannot be reached.** If a test
for it is wanted, it belongs against a concurrent-run scenario, which the risks
table records as accepted rather than handled.

```php
<?php

namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use App\Http\Requests\Api\V1\RunChunkRequest;
use App\Models\CarSearch;
use App\Services\Search\RunChunkAction;
use Illuminate\Http\JsonResponse;
use Illuminate\Support\Facades\Gate;

class RunChunkController extends Controller
{
    /**
     * Run one bounded slice of an import's outstanding searches.
     *
     * Stateless by design: the client holds no queue, and this re-selects
     * from the database each call. That is what makes a resumed run the same
     * request as the first one.
     */
    public function __invoke(RunChunkRequest $request, RunChunkAction $action): JsonResponse
    {
        Gate::authorize('run', CarSearch::class);

        $result = $action->execute((int) $request->validated()['csv_import_id']);

        return response()->json([
            'outcomes' => $result->outcomes,
            'ran_seconds' => $result->ranSeconds,
            'remaining' => $result->remaining,
            'blocked' => $result->blocked,
        ]);
    }
}
```

- [ ] **Step 3: Implement**

The loop is a `useEffect` that fires one chunk whenever `status === 'running'`
and `remaining > 0`, not a timer: a chunk request already takes up to ten
seconds, so the next goes out when the previous returns. Livewire needs a poll
because the *server* drives; here the client does.

Key details the tests pin:

- `start(total)` takes the total from `coverage.not_run`, so the bar has a
  denominator before the first chunk returns.
- `processed` counts `outcome === 'completed'`; `failed` counts
  `outcome === 'failed'`. They are not the same number and the UI shows both.
- `blocked` sets `status: 'blocked'` and **stops** — no retry.
- `pause()` sets `status: 'paused'`; the in-flight request still resolves and
  its outcomes are still counted, because the server cannot be interrupted and
  that work really did happen.
- `secondsRemaining` derives from observed pace, as
  `ListSearchQueries::runSecondsRemaining()` does: elapsed over completed,
  falling back to the configured pause plus a second until enough has run to
  measure.
- On finishing or blocking, invalidate `queryKeys.import(csvImportId)` and
  `queryKeys.searches({...})` — coverage and the query list are both stale.

**Divergence from the spec, recorded rather than silently dropped.** The spec
describes a `skipped` outcome for a row deleted or finished mid-run. This
implementation re-selects from the database each call instead of draining a
held queue, so such a row is simply not selected — `skipped` would be an
unreachable branch. Task 1 Step 4 says so, and `RunOutcomeSchema` in Task 3
accordingly enumerates only `completed` and `failed`.

**Two assumptions checked against the code before committing.**
`WikimediaClient.php:75` does read `Retry-After` off the response header, so
the block test's `['Retry-After' => '600']` reaches
`WikimediaBlockedException::$retryAfterSeconds`. And the route-collision hazard
I first wrote into Task 2 turned out not to exist — the existing
`searches/{search}` routes are `GET` and nothing binds a POST — so that note
is now advice rather than a warning.

**Type consistency.** `RunChunkResult`'s four fields map to the four JSON keys
in Task 2 Step 5 and to `RunChunkResponseSchema` in Task 3.
`useBulkRun`'s returned shape in Task 4 matches `RunProgress`'s props in Task 5.
`blocked.retry_after_seconds` is nullable in the exception, the schema and the
