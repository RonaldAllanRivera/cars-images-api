# Web-Optimized Bulk Download ZIP — Design

**Date:** 2026-05-21
**Status:** Implemented — with a correction (see below)
**Project:** cars-images-api (Laravel 12 + Filament 4)

## Correction (post-implementation)

This design assumed Wikimedia serves a thumbnail at **any** width via a
constructed URL. That is false: `upload.wikimedia.org` returns **HTTP 400**
for thumbnail widths it has not already generated (verified — 640/800/1600 px
all 400; only the API-generated 1280 px works).

What was actually shipped: the bulk ZIP downloads each image's stored
`thumbnail_url` — the ~1280 px thumbnail Wikimedia generated via the API
(`iiurlwidth`) when the image was found — and falls back to the original on
failure. This still yields ~85 % smaller ZIPs (verified: 10.94 MB → 1.63 MB
for 4 images) with zero server-side processing.

Dropped from the original design: the `download_max_width` config and the
`WikimediaThumbnailUrlBuilder` (arbitrary-width URL construction does not
work). A configurable width would require batched MediaWiki API calls
(`iiurlwidth`) at download time — recorded as a future option, not built.

The sections below are the original (pre-correction) design, kept for history.

## Goal

Make the bulk-download ZIP smaller by downloading **width-capped, web-sized** copies of each image instead of the full-resolution originals. A 4-image ZIP is currently ~11.4 MB (originals are often 3000–5000 px wide); web-sized copies bring that to roughly 1–1.5 MB.

The maximum width is configurable so it can be tuned without code changes.

## Context

- `BatchZipBuilder` currently fetches each image's full-resolution `source_url` from `upload.wikimedia.org` and writes it into the ZIP.
- Every `CarImage` already stores a `thumbnail_url` — a `1280px`-wide thumbnail generated by Wikimedia's own CDN. This proves Wikimedia serves resized images on demand.
- Wikimedia's image host serves a thumbnail at **any** width via a URL pattern (see below).
- The whole feature set is built for SiteGround shared hosting: no queue, no heavy background processing, foreground requests bounded by `max_execution_time`.

## Approach

**Use Wikimedia's thumbnail service.** Fetch a width-capped thumbnail URL instead of the original. Wikimedia's CDN does the resizing; our server does **no image processing at all**.

Rejected alternative — server-side resizing (GD / `intervention/image`): resizing hundreds of images in a single foreground request would exceed `max_execution_time` / memory on shared hosting. It also adds a dependency. The width reduction alone (e.g. 4000 px → 1600 px) removes ~85–90 % of the bytes; server-side recompression/WebP would add marginal extra savings at disproportionate cost. Recorded as a possible future enhancement, not v1.

## Wikimedia thumbnail URL pattern

Original:

```
https://upload.wikimedia.org/wikipedia/commons/4/47/Foo.jpg
```

Thumbnail at width `W`:

```
https://upload.wikimedia.org/wikipedia/commons/thumb/4/47/Foo.jpg/Wpx-Foo.jpg
```

Transformation: insert `thumb/` after `/wikipedia/commons/`, then append `/{W}px-{filename}`. The filename segment is URL-encoded in the path and the `{W}px-` prefix is prepended to that same encoded segment.

Behaviour notes:
- If the original is narrower than `W`, Wikimedia returns it at its native width (no upscaling). Acceptable.
- If the original is already small, the "thumbnail" is effectively the original. Acceptable.

## Components

### 1. Config — `config/cars-images.php`

Add:

```php
/*
|--------------------------------------------------------------------------
| Bulk download image sizing
|--------------------------------------------------------------------------
|
| Maximum width (in pixels) for images placed in the bulk-download ZIP.
| Images are fetched from Wikimedia's thumbnail CDN at this width, so no
| image processing happens on this server.
|
| Common choices:
|   1280  - typical web content width, smallest files
|   1600  - default; good size/quality balance
|   1920  - full-HD, sharper but larger
|
| Future options to consider (not implemented):
|   - a null value meaning "download originals, unoptimized"
|   - a per-download width chosen in the UI
|   - server-side WebP conversion for further savings
|
*/
'download_max_width' => env('CARS_DOWNLOAD_MAX_WIDTH', 1600),
```

Env: `CARS_DOWNLOAD_MAX_WIDTH=1600` in `.env` and `.env.example`.

### 2. New unit — `App\Services\Images\WikimediaThumbnailUrlBuilder`

Pure, stateless, unit-testable. One public method:

```php
public function forWidth(string $sourceUrl, int $width): string
```

- Recognizes a standard `upload.wikimedia.org/wikipedia/commons/{a}/{ab}/{file}` original and returns the `{width}px` thumbnail URL.
- Returns the input URL **unchanged** when it cannot safely build a thumbnail URL:
  - non-`upload.wikimedia.org` host,
  - URL already in `/thumb/` form,
  - `.svg` source (Wikimedia SVG thumbnails use a different `…px-Foo.svg.png` pattern; SVG originals are tiny anyway),
  - any path shape that does not match the expected pattern.

This guarantees the builder never produces a broken URL — worst case it returns the original.

### 3. `BatchZipBuilder` change

When fetching each image's binary:
1. Compute the thumbnail URL: `$url = $thumbnailUrlBuilder->forWidth($image->source_url, config('cars-images.download_max_width'))`.
2. Fetch `$url` (with the existing User-Agent header).
3. **Fallback:** if the thumbnail fetch is unsuccessful AND `$url !== $image->source_url`, retry once with the original `source_url`, so a thumbnail edge case never drops an image from the ZIP.
4. The ZIP entry filename and extension are still derived from `source_url` (unchanged — the thumbnail keeps the original extension for JPEG/PNG).

`WikimediaThumbnailUrlBuilder` is constructor-injected into `BatchZipBuilder`.

### 4. Scope

- **In scope:** the bulk ZIP download only (`BatchZipBuilder` / `/batch-downloads/zip`).
- **Unchanged:** single-image download (`CarImageDownloadController`) keeps serving the full-resolution original; the CSV manifest's `SourceUrl` column keeps pointing at the original.

## Error handling

- Thumbnail URL cannot be built → original URL is used (builder fallback).
- Thumbnail fetch fails → original URL is fetched instead (BatchZipBuilder fallback).
- All fetches fail → existing behaviour: `buildToFile()` returns 0, controller aborts 422 cleanly.

## Testing

- **Unit:** `WikimediaThumbnailUrlBuilderTest` — standard Commons URL → expected `{width}px` thumb URL; URL-encoded filename preserved; non-Wikimedia URL returned unchanged; already-`/thumb/` URL returned unchanged; `.svg` returned unchanged.
- **Feature:** extend `BatchZipBuilderTest` — assert the width-capped thumbnail URL (not the original) is the URL fetched; assert the original-URL fallback fires when the thumbnail fetch fails.

## Acceptance criteria

1. `config('cars-images.download_max_width')` exists, defaults to 1600, overridable via `CARS_DOWNLOAD_MAX_WIDTH`, and the config block carries the documented comment for future reference.
2. Building a ZIP fetches Wikimedia thumbnail URLs at the configured width, not the originals.
3. A non-Wikimedia or unparseable `source_url` still results in the image being fetched (via fallback) — never dropped.
4. The resulting ZIP for the existing imported images is materially smaller than the all-originals ZIP (target: roughly 1–1.5 MB for 4 images at 1600 px).
5. All existing tests still pass; new unit + feature tests cover the URL builder and the BatchZipBuilder integration.

## Out of scope (noted for the future)

- Server-side recompression or WebP conversion.
- Optimizing the single-image download.
- A per-download width/quality choice in the UI.
- An "original, unoptimized" download option.
